# Piop storage review

Source audit, 2026-09-09. This maps application-owned storage and the external storage boundaries visible in this repository. It does not inspect personal data or claim to inventory files created by arbitrary tools, hooks, MCP servers, or the separately installed Pi executable. No runtime changes or tests were made.

## Assessment

The individual formats mostly make sense: Pi JSONL for conversations, JSON for small settings, Git objects for recoverable project snapshots, and memory for live processes and rebuildable indexes. The ownership and lifecycle boundaries need consolidation. Durable user data, generated code, disposable scratch data, and shared Pi settings are spread across unrelated roots.

The highest-value changes would be:

1. Give drafts, queued input, and sidebar organization durable application storage. Queued messages currently depend on WebView localStorage, including serialized images; drafts and unsent attachments are only in memory. Keep localStorage for disposable presentation preferences. Store attachments separately from queue metadata.
2. Separate user configuration from generated extension installations. Local extension code is split between the Tauri config directory and `~/.piop`; remote code goes into `~/.piop`. Use the same logical layout on both hosts, with versioned generated resources and atomic publication. Remote staging currently truncates shared files in place with shell redirection, whereas local staging uses atomic replacement.
3. Make session lifecycle operations own the full set of related data: JSONL, diff sidecar, pending input, sidebar references, Git refs, and any temporary project directory. These currently have different owners and separate cleanup paths. Deletion of files and Git refs is not a transaction; interruption or an inaccessible repository can leave remnants.
4. Make backup/export boundaries explicit. `~/.piop` alone is insufficient: settings live elsewhere, pending input lives in the WebView, checkpoint contents live in Git databases, and system prompts may be arbitrary external files. Remote-host data must be handled on each host.
5. Give temporary files a common lifecycle with crash recovery. Several stores have normal-path cleanup but no common sweep for abandoned data. Do not treat `~/.piop/tmp` as disposable cache: it is a working directory where a conversation can create user files.
6. Decide whether fast-mode settings belong to Pi or Piop. The extension code is privately staged by Piop, but its configuration is written into Pi's shared agent directory or the project's `.pi` directory. This makes the scope surprising and differs from the private defined-agent configuration.

There is no demonstrated need to replace conversation JSONL with a database. A small backend-owned metadata store would address the fragmented queue/sidebar/draft state; its API and lifecycle matter more than whether it uses SQLite or atomic JSON.
